# Гайд по маскоту и иллюстрациям SoulTrack

Этот файл — инструкция для AI-агента (или человека), который будет генерировать,
подбирать и встраивать иллюстрации маскота в приложение SoulTrack. Следуй этим
правилам без исключений — они защищают проект и от юридических проблем, и от
визуального разлада в интерфейсе.

---

## 1. КОНТЕКСТ ПРОЕКТА

- Приложение: SoulTrack (он же LifeOS) — персональный wellness/life-tracking апп,
  соло-разработка, коммерческие амбиции.
- Целевая аудитория: **широкая, касуальная** (не биохакеры/продвинутые атлеты) —
  поэтому эмоциональный/дружелюбный маскот уместен и работает на retention.
- Текущий стек: HTML/CSS/JS (Capacitor → Android), файлы reps.html / style.css / main.js.
- Дизайн-система: тёмное premium-стекло `#05050a` фон, золотой акцент `#E8C882`,
  скруглённые карточки, только SVG-иконки (без эмодзи нигде в интерфейсе).
- Тема переключается автоматически по времени суток (день/вечер).
- У каждой метрики свой акцентный цвет (см. таблицу в разделе 4).

Маскот сейчас реализован как встроенный SVG (геометрические фигуры: круг-тело,
эллипсы-руки/ноги), красится через JS по условиям. План — заменить на
иллюстративного персонажа (картинки), с логикой выбора сцены по данным.

---

## 2. АВТОРСКОЕ ПРАВО — ЧТО МОЖНО, ЧТО НЕЛЬЗЯ

### Источник риска
Дизайн вдохновлён референс-приложением (видео из соцсети, WHOOP/Oura-подобный стиль,
с маскотом-обезьянкой в капюшоне и ростком-листиком на голове). Этот референс —
чужая интеллектуальная собственность. Задача — вдохновиться **паттернами**,
не скопировать **конкретные активы**.

### Правило разделения
| Можно (паттерн, не защищено) | Нельзя (конкретный актив, защищено) |
|---|---|
| Идея "иллюстративный маскот с разными сценами под контекст" | Конкретный дизайн персонажа (форма морды, ушей, силуэт) |
| Уровни глубины карточки (summary→detail→explain) | Конкретные тексты/фразы маскота из референса |
| Радар-диаграмма, гипнограмма, кольцо калорий (стандартные типы визуализации) | Конкретная вёрстка/CSS референса 1:1 |
| Акварельный/3D-рендер стиль отрисовки как техника | Узнаваемые детали: росток-листик на голове, зелёный капюшон, конкретные пропорции лица |
| Общая механика "маскот реагирует на метрики" | Название фич вроде "Reveal Abs" и подобные брендированные названия |

### Тест на нарушение
Перед использованием любой сгенерированной иллюстрации задай вопрос:
**"Если кто-то видел референс-приложение, узнает ли он в этом персонаже
тот же дизайн, просто перекрашенный?"**
- Если ответ "да, узнает" → генерация отклоняется, нужны более сильные изменения.
- Если ответ "нет, это просто похожий жанр" → можно использовать.

Важно: способ создания (AI-генерация вместо ручной отрисовки) **не защищает**
от нарушения. Если результат substantially similar конкретному чужому дизайну —
это нарушение независимо от инструмента. Риск особенно важен здесь, потому что
проект имеет коммерческие амбиции.

### Обязательные изменения от референса
1. **Никакого ростка-листика на голове** — это самая узнаваемая деталь, исключить полностью.
2. **Другой вид животного** — не повторять тот же силуэт обезьянки в капюшоне.
   Предпочтительные варианты: лисёнок, панда, дракончик, совёнок, енот
   (финальный вид — выбор владельца продукта).
3. **Другая одежда/атрибутика** — не худи того же кроя; либо другой тип одежды,
   либо вообще без неё.
4. **Своя цветовая гамма** — золото/янтарь `#E8C882` и тёмные тона вместо
   зелёной эко-палитры референса. Зелёный — цветовая "подпись" оригинала,
   избегать как основного цвета персонажа.
5. **Другие пропорции морды** — не повторять характерную "сердечком" форму
   бровей+щёк, которая читается в референсе.

### Что происходит при отклонении сгенерированного результата
Если сгенерированная иллюстрация не проходит тест на узнаваемость — не использовать,
перегенерировать с усиленными отличиями (см. раздел 5, промпт-структура).
Не пытаться "немного подправить" похожий результат (перекрасить, отзеркалить) —
это не устраняет сходство юридически, нужен реально другой дизайн.

## 3. ХУДОЖЕСТВЕННЫЙ УРОВЕНЬ (что оставляем как ориентир)

Референсные картинки задают полезную **планку качества**, которую стоит взять
за образец (это не защищено копирайтом, это про уровень исполнения):
- Объёмный/3D-рендер стиль или качественная мягкая иллюстрация (не плоская геометрия)
- Мягкий свет, атмосферная сцена (не персонаж на пустом фоне)
- Выразительная поза, передающая эмоцию/контекст
- Высокая детализация меха/текстуры, но не избыточная (см. раздел 4.5)

## 4. ГАРМОНИЯ С ИНТЕРФЕЙСОМ

Иллюстрация должна ощущаться частью приложения, а не стикером, наклеенным поверх.
Шесть рычагов, которые нужно контролировать при каждой генерации/подборе:

### 4.1 Цвет
- Иллюстрация обязана использовать палитру приложения, не "просто красивые цвета".
- Фон иллюстрации: прозрачный (PNG/WEBP с альфа-каналом) ИЛИ строго `#05050a`
  (фон приложения). Никогда не светлый/бежевый фон, как в акварельных референсах —
  иначе будет выглядеть "приклеенным поверх".
- Один акцентный цвет на сцену, привязанный к контексту карточки:

| Метрика | Акцентный цвет |
|---|---|
| Сон | indigo `#7B74D6` |
| HRV | pink-red `#E5677E` |
| Стресс | amber `#E8A13C` |
| Нагрузка/тренировки | orange-red `#F0764B` |
| Шаги/активность | blue `#31A8C9` |
| Вода | bright blue `#4FA8E0` |
| КБЖУ/питание | green `#66BB6A` |
| Вес/состав тела | golden-grey `#C9A876` |
| Пульс/RHR | terracotta (отдельный от HRV) |
| Привычки / нейтральный дефолт | gold `#E8C882` |

### 4.2 Свет и тень
- Направление и мягкость света на персонаже должны совпадать с тем, как светятся
  карточки в интерфейсе (мягкий рассеянный glow, не резкий контрастный свет).
- В промпт добавлять: soft ambient rim light from top, glowing edge in [акцентный
  цвет карточки], dark background.
- Резкий/театральный свет на персонаже при мягком UI-glow создаёт ощущение
  визуального разлада, даже если зритель не может объяснить, что не так.

### 4.3 Насыщенность и контраст
- Приглушённая палитра, не vibrant/яркая. При необходимости — снижать сатурацию
  на 10-15% при экспорте.
- В промпт: muted color palette, low saturation, premium aesthetic
  (не "vibrant, colorful, saturated").

### 4.4 Форма/скругления
- Силуэт персонажа и предметов сцены — округлый, без острых углов, вторя
  скруглённым карточкам интерфейса.
- Избегать резких/острых форм (острые уши, жёсткие линии, угловатые предметы).

### 4.5 Детализация линий
- Иконки в приложении — простые, line-based, единой толщины.
- Иллюстрация не должна быть гипердетализированной (текстуры шерсти волосок
  к волоску) — это создаёт ощущение "двух разных дизайнеров".
- Целиться в умеренную детализацию: semi-flat/soft-3D, не hyper-realistic.

### 4.6 Типографика рядом с иллюстрацией
- Текст/реплики маскота используют тот же шрифт-стек, что и весь интерфейс
  (`var(--f)`), тот же вес и цвет (`var(--ink)` / `var(--mut)`).
- Никаких "комиксовых" шрифтов с обводкой, никаких выносок-пузырей в стиле
  мультфильма — речевой блок маскота оформляется как обычный текстовый блок
  приложения (та же тень, тот же радиус, если есть — как у прочих карточек).

### Финальная проверка перед использованием
Наложить иллюстрацию на реальный скриншот карточки приложения и спросить:
"это выглядит как один продукт, или как будто два разных приложения склеили?"
Если второе — возвращаться к пунктам 4.1–4.6 и искать, какой рычаг не совпадает.

## 5. СТРУКТУРА ПРОМПТА ДЛЯ ГЕНЕРАЦИИ

Обязательные компоненты в каждом промпте:
1. Вид животного (НЕ обезьяна в капюшоне с листиком) — конкретный, отличный от референса
2. Явное указание "no hood" или другой тип одежды/аксессуаров
3. Цветовая палитра: акцентный цвет карточки + золото/тёмные тона, "muted, low saturation"
4. Свет: "soft ambient rim light, glowing edge in [цвет], dark/transparent background"
5. Стиль: "soft 3D render" или "semi-flat illustration", НЕ "watercolor children's book style"
   (это стиль референса)
6. Поза/эмоция, привязанная к сцене (см. раздел 6)

Пример структуры (не готовый промпт, шаблон для заполнения):
```
cute [ВИД ЖИВОТНОГО] character, no hood/[альтернативная одежда],
[ЦВЕТ ШЕРСТИ/ТЕЛА] with [АКЦЕНТНЫЙ ЦВЕТ] accent details,
soft 3D render style, muted color palette, low saturation,
soft ambient rim light from top, glowing edge in [АКЦЕНТНЫЙ ЦВЕТ],
transparent background, [ПОЗА/ДЕЙСТВИЕ ПОД СЦЕНУ]
```

### Проверка после каждой генерации
Прогнать результат через тест из раздела 2 ("узнает ли референс") ПЕРЕД тем,
как использовать картинку в проекте.

## 6. ЛОГИКА ВЫБОРА СЦЕНЫ ПО ДАННЫМ

Маскот должен реагировать на реальные метрики пользователя, а не быть статичным.
Два уровня реакции:

### 6.1 Реакция на общий индекс/метрику (глобальное состояние)
Диапазон значений → сцена:
- Готовность/индекс 80–100 → бодрая/уверенная сцена
- 60–79 → нейтральная/спокойная сцена
- 40–59 → уставшая сцена
- <40 → встревоженная/предупреждающая сцена

### 6.2 Реакция на конкретную карточку (контекстная, приоритетнее общей)
У каждой карточки может быть своя сцена, если метрика говорит что-то specific:
- HRV растёт после тренировки → уверенная/довольная сцена
- Сон короче нормы → сонная/зевающая сцена
- Стресс в норме → расслабленная сцена
- Стрик роста N дней подряд → сцена-празднование (звёздочка/огонёк/жест "ок")

### Минимальный стартовый набор сцен (не комбинаторно на каждую пару метрик)
Начинать с 5–8 ключевых сценариев, покрывающих карточки с полной 3-уровневой
глубиной (Сон, HRV, Стресс, Нагрузка) плюс общий/дефолтный, плюс стрик-момент.
Остальные вариации — через текст при той же картинке, не через новую иллюстрацию
на каждый частный случай.

## 7. ТЕХНИЧЕСКОЕ ВНЕДРЕНИЕ

- Текущая реализация маскота — инлайн SVG в reps.html (минимум 3 места:
  `status-mascot`, `activity-mascot`, `mascot-speech`), части красятся через JS
  по id (`mascot-body`, `mascot-arm-l` и т.п.).
- При переходе на картинки: заменить `<svg>` блоки на `<img src="mascot/[сцена].webp">`,
  логику "покрасить SVG по условию" заменить на "подставить нужный src по тому же условию".
- Формат хранения: **WEBP**, не PNG — критично для размера APK при большом
  количестве сцен.
- Три места использования маскота либо используют один переиспользуемый набор
  картинок, либо у каждого свой — решить до генерации, чтобы не плодить лишние ассеты.
- Для каждой новой карточки/фичи, где появляется маскот — сначала проверять,
  подходит ли уже существующая сцена по смыслу, и только если нет — генерировать новую.
